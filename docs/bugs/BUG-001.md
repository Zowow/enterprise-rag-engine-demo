## 1. Problem Description

### Actual Behavior
When a user uploads a document (e.g., `enterprise-compliance-policy.md` or `sample-policy.md`) through the Knowledge Repository interface, the UI displays:
`enterprise-compliance-policy.md #2915258f QUEUED 5% Queued in Azurite background worker queue...`
The upload remains indefinitely stuck at 5% (Queued), the document table displays 0 Chunks in `QUEUED` state, and never transitions to `Parsing (25%)`, `Embedding (75%)`, or `Completed (100%)`.

### Expected Behavior
When a document is uploaded:
1. It is stored in Blob storage and enqueued into Azurite `document-ingestion-queue`.
2. The background ingestion worker immediately dequeues the job, extracts content, chunks text, generates vector embeddings in Qdrant, and updates PostgreSQL database status to `Completed` with valid chunk counts.
3. SignalR emits real-time progress transitions through 25%, 75%, and 100%.
4. The background worker service container must have resilient auto-restart configurations (`restart: unless-stopped`) so system reboots or Docker restarts do not leave it in an unrecoverable offline state.

### Reproduction Steps
1. Navigate to the web application at `http://localhost:3002/`
2. Upload a policy document (`enterprise-compliance-policy.md` or `sample-policy.md`)
3. Observe the progress bar stuck at: `QUEUED 5% - Queued in Azurite background worker queue...`
4. Check docker container status: `docker compose ps` shows `worker` is not running (`Exited (255)`), because `worker` was omitted from container restart policies in `docker-compose.dev.yml`.

### Step 2B: Minimal Surgical Fix (GREEN)
* **Root Cause:**
  1. `worker` (and `frontend`) service in `docker-compose.dev.yml` lacked `restart: unless-stopped`. Following a system/daemon reboot, the worker container stayed in `Exited (255)`, leaving queued ingestion jobs in Azurite unconsumed.
  2. In `backend/src/Api/Hubs/IngestionHub.cs`, the server hub class lacked the `IngestionProgress(IngestionProgressUpdate update)` method, preventing worker SignalR client progress invocations from being relayed to frontend clients.
  3. In `frontend/src/hooks/useIngestionSignalR.ts`, `joinJob` did not await connection completion if called during initial connection handshake.
* **Files Modified (Minimal Diff):**
  * `docker-compose.dev.yml` (Added `restart: unless-stopped` to `worker` and `frontend`)
  * `backend/src/Api/Hubs/IngestionHub.cs` (Added `IngestionProgress` method broadcasting to clients)
  * `backend/tests/EnterpriseRAG.UnitTests/SignalRNotifierTests.cs` (Added unit test for `IngestionProgress`)
  * `frontend/src/hooks/useIngestionSignalR.ts` (Resilient `joinJob` connection check)
